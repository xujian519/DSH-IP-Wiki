# 已知缺口与已验收批次

> 这是本项目的诚实台账。**没有做到的事**、**做到但必须知道边界的事**、以及**还没定的事**都在这里写清楚，别当成已完成。
>
> 台账的规矩：缺口补上了就把它改成事实（带证据），不是删掉；每条缺口要么带复现命令，要么带指向证据的链接。

## 开放的缺口

### 无浏览器真机验证

渲染与交互由 jsdom 覆盖，从未在真实页面里点过。面板席位、路由、数据都有实测证据（见 [README](../README.md)），但「看得对不对」没有验证过。**面板视觉与安全一轮（2026-09-29）改完仍未真机核对**：亮暗对比度、40 字版心、30px 行高都是按令牌取值与代码算出来的，不是截出来的（[决策记录](notes/implemented/2026-09-29-panel-visual-and-safety-pass.md)）。

### dispose 断言只做过一条

`ctx.effect` 的写法有规定（[architecture.md](architecture.md) 第 7 条），但"卸载后注册真的移除了"长期没有测试证明。**2026-10-02 补了第一条**：启动预热那条 effect 的清理函数被断言过——`tests/search.spec.ts` 让第一批嵌入悬在半空、调用清理函数、再放行，断言第二批从没被请求过。

其余三条 effect（路由、工具、指引段）仍然只断言"注册了什么、清理函数被调用过"，没有断言"卸载后真的不再生效"（`tests/host-entry.spec.ts` 的 stub 把 `disposed` 记成 `route` / `tool:<name>` / `guidance`，那是 stub 自己写的标记，不是被测对象的行为）。

### CI 曾经一次都没跑过（已修）

2026-10-02 起有了本地钩子（`lefthook.yml`：pre-commit 暂存文件 lint + 空白、pre-push typecheck）与 CI（`.github/workflows/check.yml`：一条 job 跑 `pnpm run check`），仓库也 `git init` 了（[决策记录](notes/implemented/2026-10-02-local-hooks-and-ci.md)）。同日接上远端，**workflow 第一次执行就通过**：`check` 在 ubuntu-latest 上 success（运行 `37028718041`，30 秒，`pnpm install --frozen-lockfile` 与 `pnpm run check` 逐步全绿）。这只是第一次执行，仍然缺平台矩阵（只有 ubuntu + node 22），`pnpm run build` 的 `client-shape` 门禁也不在 CI 覆盖面内。

### 语义级曾经在真机上从未执行过（已修）

**2026-10-02 已修**，留在台账里是因为它记着一个值得记住的形态：一条从没在真机上生效过的能力。

起因：真库 1,155 张卡片一次整批提交本机端点，`HTTP 200`、1,155 条向量全部返回，耗时 **107.5 秒**，而部署配置 `embedding.timeoutMs` 是 **20000**；而 `embedCorpus` 一次提交全部、`AbortSignal.timeout` 罩整批、向量只在整批成功后才写内存——于是缓存**暖不起来**，每次检索都先等满 20 秒超时再退回关键词。验收口 `p1-eval` 早就绕开了它（`timeoutMs: 240_000`），所以评测量的是管线、部署跑的是关键词。

修法与三次真库实测（冷 **498.51 s** → 热 **79.72 s** / **80.22 s**，缓存 1,155 条 / 6.4 MB，20 题在部署的 20 秒下全部走 `rerank`）见[向量缓存落库外与启动预热](notes/implemented/2026-10-02-vector-cache-outside-library.md)。仍然没做的是：面板不轮询预热进度，预热与检索并发时不互斥。

### 文档门禁没有字数预算

两道文档门禁只管链接与笔记格式，没有 harness 那样的字数上限（`verify-doc-budgets`）。文档变长目前只靠 review 管。

### 指向仓外的「设计文档 §N」引用无法核对

[README](../README.md) 与两条决策记录里引用了「设计文档 §23–§24」「方案 §4」这类**仓库里不存在**的文件与段落号，门禁看不见（它不是 Markdown 链接），只能靠人核对——这是"别在正文里写会漂移的引用"的反例。有证据价值的结论那几条记录里已经有，引用留着是为了回溯当时的讨论。

### 面板删除没有服务端二次校验

`/card/delete` 的服务端不认"确认"标记：重放同一个请求就会再删一次。面板侧只有"误点保护"（danger 变体 + 二次确认行），拦不住脚本或重放。放弃"确认令牌"的理由记在[删除审计线](notes/implemented/2026-09-29-delete-audit-line.md)。

## 事故

### 删除在真库上意外演练过一次

2026-09-29，`/card/delete` 的破坏性负控制**把控制脚本跑在了真实库根上**，删掉了 `cards/rule/wiki-救济-原理-永久禁令救济-拆分-01-1.-基本规则-f8671f2e.md`，并按设计剥掉了 `29526e84` 那张卡上指向它的一条反链。两处都从 `.dsh-ip-wiki/archive/` 里的确认草稿按字节写回，索引重建后 1,137 张、`duplicate-title` 回到 8 条。当时 `log.md` 里没有删除行（**已修**：删除现在写一行审计），定位只能靠对比 `index/` 的历史备份。自此"破坏性验证只对副本或临时目录跑"成为常驻军规（[testing.md](testing.md#破坏性验证的规矩)），删除的正式验收仍只走临时库 + 真 socket（`tests/delete.spec.ts` / `tests/routes.spec.ts` / `tests/host-entry.spec.ts`）。

## 已验收批次

事实，不是缺口；列在这里是为了让"哪些面已经过关、过的什么关"有唯一的落点。

### P1–P4

- **检索**：三级管线 + 逐级降级 + 面板检索框。真库 139 张实测命中@1 = 17/20、命中@3 = 19/20，全部由精排级排序（20 题里有 4 题的金标卡已被合并取代，金标改以合并卡为正解，同轮沿用旧金标为 14/20、16/20）。
- **素材 → 卡片闭环**：草稿 + 差异预览 + 确认 + 回滚 + 来源分级 + 审计，三份真实素材实测通过。
- **质量门禁**：确定性规则分三档 + `failOn` 结论 + 面板报告 + 真库实测 0 critical / 0 warning / 61 suggestion + 三条注入失败用例。
- **确认入库**：`ip_wiki_confirm` 把已入库的 `status: draft` 卡提交为「状态确认」草稿（`kind: 'status'`，确认时按磁盘现算只翻 `status` 一行），面板「全部确认 / 回滚整批」逐份调用既有写路由；真库副本实测把 117 张在用卡放回 `status: draft` 后提交 → 确认 → 回滚，**树哈希逐字节复原**，门禁 finding 计数不受影响。
- **合并落库**：合并草稿（`supersedes`）确认后写合并卡并把被弃用的卡标成 `status: deprecated` + `superseded_by`（正文只改 `status` 一行、加 `superseded_by` 一行，可逐字节回滚）。真库落库结果：9 组 22 张逐字同题 → 139 张卡、117 在用 / 22 已废弃，重复标题 finding 22 → 0、断链仍为 0、索引 139/139 无漂移；9 份整批回滚树哈希复原（[记录](notes/implemented/2026-09-29-merge-supersede-rollback.md)）。被弃用的卡不再计入重复/孤立规则，也不再抢答——检索把它们排在**所有在用卡之后**（[记录](notes/implemented/2026-09-29-deprecated-cards-rank-last.md)）。
- **索引重建闭环**：`rebuildIndex` 只覆盖它拥有的字段（迁移写的其它键原样保留）+ 写卡片后自动重建 + 面板「重建索引」按钮 + `POST /index/rebuild`；`confirmDraft` 把旧索引字节并入草稿备份、`revertDraft` 放回旧字节，所以 confirm→revert 逐字节复原。
- **面板视觉与安全一轮**：中性面改从墨水派生、色相只留给状态、正文 40 字版心、标题分三档、树行定高 30px、补 `:focus-visible` 与链接规则、按钮按读/写/销毁分四档、「全部确认（N）」先展开确认行再开写并报「正在落库 N/总数」、错误横幅接线「重试」。五条负控制真变红，其中状态色那条**第一版是假门禁**（按行首锚定的正则量不出原始缺陷），重写后才有牙（[记录](notes/implemented/2026-09-29-panel-visual-and-safety-pass.md)）。

验收命令与仍然红着的声明线见 [development.md](development.md#验收评测) 与 [README](../README.md#检索)。

### Wiki 批次导入

`scripts/import-wiki.ts` 把 vault 的 998 页导入真库（139 → **1,137 张**，已确认 117 / 未确认 998 / 已废弃 22），索引无漂移、导入卡 3,499 条 `related_concepts` **0 断链**、门禁 findings 61 → 422（`duplicate-title` 8 = 4 组源内同题、`low-confidence` 248 待人工看、`orphan-card` 84、`unclassified` 82）。判定口径见[决策记录](notes/implemented/2026-09-29-wiki-import-mapping.md)，库侧报告 `reports/wiki-import.md` / `reports/wiki-import-dry-run.md`。

> **库在这之后又长过**：2026-10-02 门禁实测是 **1,155 张**（已确认 133 / 未确认 959 / 已废弃 63）。多出来的 41 张已废弃正是"近重复去重"那 20 组 41 张冗余卡——它们**已经落库了**（不再是待确认草稿）；另有 18 张新卡与 16 张新确认的卡，来源在本插件的记录之外。下面这段"导入后"的实测数字仍按下表记的 1,137 张来读。

导入后同一套 20 题的检索实测是**命中@1 = 13/20、命中@3 = 16/20**（声明线 14/18 仍红着）。两轮已修：①候选池把两阶段分数混在一起截断，导致向量级排第 5/6 的金标卡进不了精排，现每阶段保底席位（[记录](notes/implemented/2026-09-29-recall-pool-stage-share.md)）；②池子 20 → 40 席、保底席位随之从 10 提到 20——有一题的金标在关键词级第 20、向量级第 19，20 席刚好挡在池外，40 席进池后精排把它排到第 2（[记录](notes/implemented/2026-09-29-pool-size-and-near-duplicates.md)）。**上一轮那句「剩余差距是精排更偏爱同族卡」已被实测否掉**：源页≤1 / 主题≤2 / 主题≤3 三种限席与排名融合都做了端到端对照，指标一个不差或更差；剩下 4 题是精排给同主题材料打了更高的分，而唯一能让指标过线的「整理层整层优先」（17/20、18/20）会降低部分题目的答案质量、且在金标全取自整理层的验收上是自我印证，**未采纳**。

### 近重复去重

判重不再只看标题。库侧 `tools/near_duplicates.py` 给每一对卡算三个信号（嵌入余弦 / 正文 5-gram 精确 J / **覆盖率**），合并判据是**覆盖率 ≥ 0.90 且 J ≥ 0.30**；已合并的 9 组是它的正控制（9/9 召回）。真库 1,137 张量出 **20 组 41 张**冗余卡（覆盖率 0.90–1.00；9 组"主内容 + 它的拆分片段"、8 组 vault 两棵树各存一份同文、3 组同目录同文两页），其中 1 组在已确认卡之间。`scripts/merge-duplicates.ts --groups <文件.json>` 用同一套组装/备份/回滚写了 20 份合并草稿（[记录](notes/implemented/2026-09-29-near-duplicate-coverage-criterion.md)）。

同轮量出的两件事：①门禁 `duplicate-title` 剩下的 4 组**都不是重复**（组内 J < 0.15、覆盖率 < 0.5，`权利要求解释` 那两张是 531 字与 19,309 字的两份不同文档），正确处置是**改标题**；②复核早前 9 组合并，22 张被吸收卡里 **13 张**在合并卡中的覆盖率只有 0.41–0.80——原文仍在库内（`deprecated`），但"只留一张"并未真正成立，作为证据记录，不回滚（用户已确认过）。
