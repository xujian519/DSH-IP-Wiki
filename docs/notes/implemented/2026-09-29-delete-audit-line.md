# Note: 永久删除留一条审计线（事故复盘）

Status: implemented

## Problem

`/card/delete` 是本插件**唯一不可撤销**的写入，也是唯一**不留任何痕迹**的写入：`confirmDraft`、`discardDraft`、`revertDraft` 各写一行 `log.md`，`rebuildIndex` 也写一行，删除只写了索引那行。

这个缺口是被一次真实事故量出来的。2026-09-29T15:41:04Z，真库少了一张卡（1,137 → 1,136）：

- `log.md` 里没有 `delete` 行，唯一的证据是一行光秃秃的 `index rebuilt 1136 cards backup …`——`deleteCard` 内部调 `rebuildIndex` 就是这个形状。
- 少的是 `cards/rule/wiki-救济-原理-永久禁令救济-拆分-01-1.-基本规则-f8671f2e.md`，只能靠对比 `index/` 的历史备份才能定位（`byStatus`、id 集合逐张比对）。
- 它的反链也按设计被剥掉了：`cards/rule/wiki-救济-原理-永久禁令救济-29526e84.md` 的 `related_concepts` 由 4 条变 3 条（mtime 与索引重建同一分钟）。
- **卡片正文不是从任何备份找回的**：`.dsh-ip-wiki/backups/` 里没有它（删除不备份）。它在 `.dsh-ip-wiki/archive/<草稿 id>.json` 里——导入时的确认草稿保存了卡片全文。两处（卡 + 反链）都按归档字节逐字节写回，索引重建后 1,137 张、`duplicate-title` 回到 8 条并已复核。

事故来自本轮的破坏性负控制：验证删除路径时，控制脚本跑在了**真实库根**上，而不是副本。插件侧无法阻止这件事（`deleteCard(root, path)` 对任何 root 都照做），所以既修产品也修流程。

## Decision

1. **删除在 `rm` 之后、`rebuildIndex` 之前写一行审计**：`delete <path> <n> references stripped`。放在重建之前，是因为重建自己会写行、也会失败；删除这一步一旦发生就必须已经留痕。测试断言两种形态（1 条反链 / 0 条反链）。
2. **负控制**：删掉那行 `logLine` 调用后 `tests/delete.spec.ts` 有 2 条测试变红（并且先断言"变异确实落地"——本轮之前曾出现控制脚本改错目标却报绿）。
3. **流程规则进规范**：破坏性验证只对副本或临时目录跑，**永不对库根跑**（[边界](../../../AGENTS.md#边界)）。同一轮里 `deleteCard` 的真实入口覆盖仍是临时库 + 真 socket。

## Alternatives considered

- **删除前把卡片字节备份进 `.dsh-ip-wiki/backups/`** —— 落选：用户在面板决策时就选了"永久删除、不可回滚"，藏一份可复原的副本与那条承诺矛盾。审计线记的是"删了什么"，不是"怎么恢复"。
- **删到一个 trash 目录、由人来清** —— 同上，等于偷偷把"不可回滚"变成"可回滚"。
- **在删除路径上要求服务端二次确认标记** —— 落选：现在会重放同一请求就再删一次，但加一个"确认令牌"只是在客户端与服务端之间转移一个布尔值，挡不住控制脚本这种事（本次事故是**我的**脚本主动调用），却增加一层契约。真问题是"别对真库跑破坏性验证"。
- **只修流程、不给删除加日志** —— 落选：这次靠索引备份反推是运气（那张卡恰好也出现在归档草稿里）；下一次可能连反推的锚点都没有。

## Consequences

- 换来：任何一次删除都能从 `log.md` 一行读出卡片路径与被剥掉的反链数；真库那次事故的复盘有了确定证据链（时间、路径、反链、恢复来源）。
- 换来：[TECH_DEBT](../../TECH_DEBT.md) 里"删除没有真库演练"这条缺口改了措辞——它**意外地在真库上演练过一次**，结果是"卡被删、反链被剥、可逐字节复原"，因此这条缺口现在带事实而不是假设。
- 付出：删除多一次文件写入（失败不影响删除本身与否，`logLine` 失败会让 `deleteCard` 抛错——此时卡已删、审计缺失，与"先删后记"的取舍一致：宁可报错也不静默）。
