# Note: 已废弃卡仍可被检索，但永远排在任何在用卡之后

Status: implemented

## Problem

9 组逐字同题合并落库后（真库 139 张：117 在用 / 22 已废弃），真机检索暴露了排序缺陷。问「技术启示」，前 3 条都是 `状态：已废弃`，合并后的正解排第 4：

```
1. 如何判断现有技术是否给出了将区别特征应用…状态：已废弃
2. 如何判断现有技术是否给出了将区别特征应用…状态：已废弃
3. 如何判断现有技术是否给出了将区别特征应用…状态：已废弃
4. 如何判断现有技术是否给出了将区别特征应用…（合并卡）
```

根因：`search.ts` 只按分数排序（`right.score - left.score || path`），`status` 只在结果里标注、不参与排序。同一问题的多版答案本来就几乎逐字相同，精排分数分不出高下，于是被取代的正文照样递到使用者与模型面前——**合并想消除的状态被检索层原样保留了下来**。

## Decision

1. **排序加一条优先键**：`byRank` = 在用优先 → 分数降序 → 路径。候选池的两次排序（召回合并后、精排重排后）统一用它；截断 `slice(0, CANDIDATES)` 发生在排序之后，所以在用卡不会被已废弃卡挤掉精排名额。
2. **不隐藏，只下沉**：已废弃卡仍会出现在结果里（延续既有的“标注状态、不隐藏”取向），但排在所有在用卡之后；只有在用命中不足 `limit` 时才会露头。
3. **计数上桌**：`SearchResult.deprecated` 报出本次扫描里有多少张已废弃卡；工具结果头写「已废弃 N 张排在末尾」，面板结果头写「已废弃 N」。
4. **测试带负控制**：新测试写一张把查询词重复多次的已废弃卡——纯 BM25 下它必然第一——断言它排第二、且 `hits[0].score < hits[1].score`。去掉优先键后该测试立刻变红（实测 gamma 反超 alpha），恢复后转绿。

## Alternatives considered

- **完全排除已废弃卡** — 落选：使用者可能记得旧措辞，面板卡片树本来也展示它们；排除还会让“合并卡吸收了哪些卡”在检索侧不可见。且这与既有的“标注状态、不隐藏”取向相反。
- **只在渲染层排序**（面板与工具各自处理）— 落选：本项目的既有约束是“模型与面板不会给出不同答案”（同一套实现）；在两处各排一次必然漂移。
- **给已废弃卡降权而不是分区**（如乘 0.5）— 落选：分数是精排给的相似度，掺进生命周期语义后没人说得清顺序由哪一半决定；分区是确定的，断言也直接。
- **把已废弃卡从 `scanned` 里剔除** — 落选：`scanned` 回答“读了多少张”，读就是读了；另给 `deprecated` 计数，两个事实各自成立。

## Consequences

- 换来：合并后的正解不再被它取代的正文压住。真库实测（真端点 + 真库 139 张）：「技术启示 创造性 判断」前 5 条全为在用卡，合并卡以 0.9856 居首；「专利无效宣告程序的流程和请求人资格」合并卡以 0.9989 居首。
- 付出：`SearchResult` 多一个字段（Host 与 Client 同批发布，路由前缀与守卫头未变）；已废弃卡在这一排序下实际很难被检索到——这是设计意图，代价是“去翻旧措辞”要靠面板卡片树或合并卡正文末尾的「合并说明」表。
- 金标口径随之调整：`p1-eval` 的 20 题里，4 题原本指向被合并掉的卡，金标改为优先认合并卡（旧卡仍列在 `wanted` 里，因为它们确实承载那段措辞）。**改金标前后不是同一把尺子**：旧金标实测 命中@1 = 14/20、命中@3 = 16/20；新金标实测 17/20、19/20。两个数并列记录，不当作“修好了涨 3 分”的证据——修排序之前（同旧金标）没有测过，缺那一格。
