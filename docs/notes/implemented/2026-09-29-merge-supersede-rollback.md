# Note: 合并落库 = 只加两行 + 被弃用的卡退出重复/孤立规则

Status: implemented

## Problem

去重候选（本地嵌入 7/7 + `duplicate-title`）早就出得来，但"合并"一直停在提案层：没有一条把两张重复卡收成一张、并且**能原样退回**的路径。这里有两个真问题：一是被合并掉的卡怎么处置（删掉？改写？），二是合并修好了问题、门禁却可能永远红着。

## Decision

1. **被弃用的卡只加两行，正文一字不改**：`status: "deprecated"` + `superseded_by: "<合并卡路径>"`。用 `setFrontmatterFields()` 逐行改写顶层字段，嵌套键与正文保持逐字节不变（测试断言"正文按 `---` 切开后完全一致"）。原文因此永远留在库里，符合方案 §5.1"保留原文与 supersedes 链"。
2. **被弃用的卡退出"重复标题 / 孤立卡"两条规则**：这两条问的是"在用库"的一致性；否则一次成功的合并会让门禁永久红灯，等于门禁在惩罚修复。卡片阅读器显示「已被取代 → 合并卡路径」。
3. **合并草稿的幂等键含 `supersedes` 集合**：同目标同内容但弃用集合不同是两个草稿；集合顺序无关。
4. **备份按目标路径分层**（`.dsh-ip-wiki/backups/<草稿 id>/cards/rule/x.md`）：一次合并要备份多份，扁平命名会撞名。**派生索引也进这份备份**（`.../index/card-index.json`）：确认会重建索引，回滚必须把旧字节放回去，否则 confirm→revert 不再逐字节复原（这一条是验收用例抓出来的——先按"回滚后再重建一次"实现，哈希比对立刻变红）。
5. **先写合并卡、再标被弃用卡**：崩溃时留下的是"两张重复卡"，而不是"指向一张并不存在的合并卡的弃用卡"。
6. **弃用集合在起草时校验**：越界路径、指向自己的卡、重复列出、库里没有的卡，一律拒绝。

## Alternatives considered

- **合并后删除被弃用的卡** — 落选：库里删除不可逆（只能靠备份），而"保留原文 + 标记取代"既满足方案要求，又让审计与回滚都简单。
- **改写被弃用卡的正文（例如加"已合并到 X"）** — 落选：那会改变用户写下的原文，也让 diff/哈希复原变得不可能。
- **合并后仍让重复标题报警（把它们看作"待归档"）** — 落选：门禁会永久红着，掩盖真正的新重复；要表达"历史重复"就不该用 warning。
- **在草稿里只记合并卡、由用户自己改被弃用的卡** — 落选：人被要求做机械的两行编辑，且没有备份与回滚保证。

## Consequences

- 换来：合并可一键完成、可逐字节回滚、原文不丢、门禁数字真实下降（真库副本实测重复标题 4 → 2）。
- 付出：规则多了"在用/历史"的区分（`status !== 'deprecated'` 影响两条规则），需要记住；被弃用的卡仍参与其它规则（空正文、断链仍会被报）。
