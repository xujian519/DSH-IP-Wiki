# Note: B 档面板改造 + 卡片永久删除

Status: implemented

## Problem

用户原话：「继续B档，且目前只有确认入库，没有删除的入口」。

**B 档**是上一轮列出的未做项，其中一件是立项理由本身：正文 `[[…]]` 是死文本、「相关卡片」只显示一个计数，而全库有 **5,405 处**正文链接与 **3,499 条** `related_concepts`——「不用再打开 Obsidian」靠的正是互链，此前是空的。其余：1,137 行的树默认全展开（约 63,800px / 71 屏）；无标题过滤；卡片头把 id/path 当一等内容平铺，且卡型与 `superseded_by` 各渲染两遍；门禁 422 条 finding 全量铺开；正文首个 `#` 标题与卡片标题重复渲染（真库 1,262 个一层标题里绝大多数就是卡片标题）。

**删除**：插件此前没有任何删除路径。写入面只有四条 POST，且都被设计成可回滚；`cards/` 只被 `confirmDraft` 写。

## Decision

### 1. 卡片永久删除（用户选：永久、不可回滚；同批清关联）

新 POST `/card/delete`（body `{ path }`），实现 `deleteCard(root, path)`（`src/host/delete.ts`）：

- **只接受 `cards/**/*.md`**：`..` 段、`reports/`、`index/` 一律拒绝，调用方给的路径再过一次包含关系判定；引用卡片的路径来自本库自己的目录遍历，因此按构造就在根内（这条写在代码注释里）。
- **先清引用，最后删卡**：其它卡 frontmatter 里指向它的 `related_concepts` 先逐条移除（`removeFromListField`：行级手术、其余字节不动、清空则塌成 `[]`），全部写完才 `rm` 目标文件。中途失败留下的状态是「关联少了几条、卡还在」——可重跑、可被门禁看见；反过来（先删卡）会留下悬空引用。
- **按 id 与 `from_id` 两个名字匹配**：门禁的 `broken-link` 也是按这两个名字解析，所以删完断链仍为 0。
- 最后 `rebuildIndex`；返回值 `{ path, title, stripped, totalCards }`，Client 侧由 `parseDeleteResult` 逐字段读入。
- **不可回滚**，这是本插件第一个不可撤销的写操作，所以：面板上是 danger 变体 + 二次确认行（文案写明「此操作不可回滚」），执行后横幅报「已删除 X / N 处关联已清掉」+「知道了」。**不给模型工具**：没有 `ip_wiki_delete`，删除入口只存在于面板——永久删除需要一个人工复核点，而工具一旦注册，模型就能在没有面板的地方调用它。
- **写入面因此是五条 POST**，[架构约束](../../architecture.md#不可违反的架构约束)同步改写并记下这条例外（"都可回滚"不再成立）。

### 2. B 档

- **互链可达**：`linkResolver(tree)` 建四轴索引（id / title / 文件名干 / 页面名——页面名是导入文件名去掉 `wiki-` 前缀与末尾 8 位 revision）。正文 `[[…]]` 与「相关卡片」都能点开；**解析不出来的保持纯文本**，不做"看起来能点却点不动"的第三态。相关列表里解析不到的 id 后来改成灰字加「不在库内」，仍不可点，见[卡片阅读器方案 A](2026-11-02-card-reader-scheme-a.md)。
- **树的规模**：域分组默认收起（一级是地图，不是 1,137 行流水）；`Shift+X` 全展 / 全收；树内**按标题过滤**（纯前端、零请求），命中时用扁平列表替换分组视图。
- **卡片头**：卡型 / `superseded_by` 不再在 facts 里重复；置信度、质量、辖区、法条、来源、id、path 收进 `<details>`「元信息」；相关卡片从计数变成可点列表。
- **目录**：`headingsOf(body)`，**≥2 个标题**才渲染；与卡片标题重复的那个一层标题既不重复渲染、也不列进目录，所以目录里每一项都真的能跳。默认展开的折叠、相关框与删除行的现行布局见[卡片阅读器方案 A](2026-11-02-card-reader-scheme-a.md)。
- **门禁折叠**：finding 按三档折叠，critical / warning 默认展开、suggestion 默认收起（真库 422 条里绝大多数是最轻那档）。
- **本轮不做**：密度开关、树列拖拽。收起 + 过滤已经解决"扫不动"，这两个旋钮没有实测需求，却各要一套状态与交互测试；留在 B 档清单里。

### 3. 量到的两件事（写下来免得下次再踩）

1. **这个 frontmatter 方言只认缩进的块式列表**：`related_concepts: ["a", "b"]` 被读成**字符串**（`textList` 返回空数组），不缩进的 `- "a"` 也读不出来（两种都实测过）。所以行级删除器只处理块式与 `[]`——我第一版按"两种列表形态"实现的 flow 分支是**死代码，已删**；那两种写法本来就不构成引用，门禁也看不见它们。
2. 真库 1,137 张卡的 `related_concepts` 全是块式或 `[]`，与上面的限制一致；`cards/` 下没有内联列表写法。

## Alternatives considered

- **删除走草稿、可回滚**（我推荐的方案，用户选了永久）：草稿制能把删除也纳入「都可回滚」这条不变量，但用户明确要不可回滚的删除入口，且永久删除更贴合"清掉废卡"的用途。代价已写进[架构约束](../../architecture.md#不可违反的架构约束)：写入面第一次出现不可撤销操作，且它**没有** `confirmDraft`/`revertDraft` 那套备份兜底。
- **只删卡、不清关联**：实现最小，但会在一个断链为 0 的库里立刻造出断链（真库 3,499 条关联边），由门禁报出来等人清。用户选了同批清。
- **删除也注册成工具**：不做，理由见上（永久删除没有人工复核点时不该给模型）。
- **给删除做 `.dsh-ip-wiki/deleted/` 隔离区**：那样它就不是"永久删除"了，与用户的选择冲突；真要在文件系统层面找回，备份/快照是更合适的地方。
- **虚拟列表**：仍不做（会打翻现有断言、jsdom 无 `IntersectionObserver`、要引依赖）。收起 + 过滤已把首屏行数从 1,385 降到四十余个分组头。
- **密度开关 / 树列拖拽**：不做，见上。
- **目录做成常驻右栏**：本轮先做成正文上方的可折叠块（≥2 个标题才出现）。常驻栏要动阅读区的三栏布局，属于下一档。方案 A 明确不做第三栏和 sticky 迷你条，见[卡片阅读器方案 A](2026-11-02-card-reader-scheme-a.md)。

## 负控制

五条真变红（每条先备份、跑完逐字节还原）：

1. 删卡时不清关联（把 `writeAtomic` 那句换掉）→ `delete.spec` 红；
2. 去掉 `cards/` 与包含关系守卫 → `delete.spec` 红；
3. 删除按钮直连 `deleteSelection`（去掉二次确认）→ `panel.spec` 红；
4. 行级删除器改成"不删任何项" → `frontmatter.spec` 红；
5. 把标题过滤改成恒空 → `panel.spec` 红。

**两条假控制，都先当作"通过"**：

- 第一条是上一轮遗留的同款：把 `color:` 断言写成按行首锚定的正则——变异不变红，回头拿同一把尺子量**原始缺陷代码也量不出来**，已重写为「先剥离 `border-*color` 声明再断言状态色不作文字色」。
- 第二条：删除二次确认那条控制第一次的 perl 模式写的是 `onClick`，而真实代码是 `onAskDelete`——**模式没匹配上、代码一个字没改，却报了绿**。重做后红。教训：控制脚本必须自己断言"变异真的落地"（本轮后半段已加 `diff -q` 自检）。

## Consequences

- `pnpm run check`：typecheck、oxlint `--deny-warnings` 0 warning、**521 通过 / 7 跳过**、`src/**` 每文件四项 100%。
- 删除的端到端证据在测试里走真实 socket（`tests/routes.spec.ts` 起真服务器）与真实磁盘（`tests/delete.spec.ts` 写真临时库），另有 `host-entry` 里经注册表的 handler 一路打到磁盘。
- **未做**：真机视觉验收（[TECH_DEBT 里这条既有缺口](../../TECH_DEBT.md#无浏览器真机验证)）；本轮的删除**没有**在真库 1,137 张上演练过——它是永久操作，验收只走到临时库与真 socket。
