# Note: 检索分三级、每级可降级、库内不落任何派生物

Status: implemented

## Problem

P0 只能按卡型与域浏览。真实用法是带着问题来（"审查员说修改超范围怎么判断"），需要在 Harness 里直接得到命中的卡片与出处。同时有两处约束必须同时满足：本机嵌入端点可能没开（不能因此搜不了），以及知识库是用户的东西（不能因为检索而往库里写派生物、更不能动卡片）。

## Decision

1. **三级管线、逐级降级**：关键词（BM25）→ 本地嵌入召回（bge-m3）→ 本地精排（bge-reranker-v2-m3）。任一级不可用或报错，就在结果里写明 `degraded` 并退回上一级，**请求不失败**；`mode` 字段说明实际是哪一级排的序。
2. **关键词索引在内存里现建**，不用 FTS5 落盘：库规模（数十到一两千张卡）内存打分毫秒级，卡片改动立刻生效，不需要重建步骤，也就不需要往库里写索引文件。
3. **向量缓存只在进程内存**，键是"路径 + 内容摘要"：卡片一改，键就变，旧向量自然失效；进程重启后第一次检索重新嵌入。**不写 `index/vectors/`**（方案 §4 曾把它设计为落盘缓存）——库的写入面留给 P2 的草稿确认机制，P1 保持库只读。
4. **单字 CJK 只作兜底**：文档同时索引单字与二字组（否则一字查询命中不了），但单字只在"没有任何更强的词命中"时才参与打分。否则"商标注册"会因为共享一个"标"字而召回讲"标准"的卡片。
5. **引用可核对**：`ip_wiki_cite(path, quote)` 逐字（忽略空白）核对引用是否真在卡片里，命中则给上下文，不命中就报"没有这段原文"。这是把"引用可逐条核对"变成可执行的检查，而不是一句承诺。
6. **密钥在库外**：`~/.dsh/ip-wiki/config.json`（0600），路径由 `embedding.apiKeyFile` 配置；读不到只降级、不报错。

## Alternatives considered

- **FTS5（`index/fts.sqlite`）** — 落选：要引入 sqlite 依赖与一个落盘派生物，而 BM25 在内存里对两千张卡毫秒级；落盘索引还带来"什么时候重建"的状态问题。
- **向量落盘到 `index/vectors/`** — 落选：检索本来就不该写库；内存缓存的失效语义（按内容摘要）比落盘缓存简单得多，代价只是重启后首查慢一点（实测 20 题 34 秒，其中大部分是首查嵌入）。
- **嵌入不可用就报错** — 落选：本机端点是否在跑是环境状态，不是用户的操作错误；降级到关键词仍然能搜到（实测关键词路径独立可用）。
- **只索引二字组** — 落选：一字查询（"权"）就完全命中不了；只索引单字又太吵。因此"单字兜底、强词优先"。

## Consequences

- 换来：端点没开也能搜；库里不留任何插件产物；卡片改动即时生效；引用可机器核对。
- 付出：进程重启后第一次语义检索需要重新嵌入整个库（当前 30 张可忽略，1235 张量级需要关注）；单字兜底仍会带来少量弱命中（排在强命中之后，分数低）。
- 实测（**30 张试点库**，20 题真实业务问题，真端点 + 真库）：**命中@1 = 18/20，命中@3 = 20/20**，20 题全部由"精排"级排序；未列首位两题为"相关卡片排前"（问题 5 命中第 2、问题 11 命中第 3），复核记录见设计文档 §12。
- 这几个数字只对当时的 30 张库成立：全量迁移后同一套题是 14/20 与 19/20（金标随库补全后 17/20 与 19/20，见设计文档 §17.4），9 组合并落库并修掉"已废弃卡抢答"之后是 17/20 与 19/20（§20.4）。**当前口径以 README「检索」与 `tests/p1-eval.spec.ts` 为准。**
