# Note: 对照 llm_wiki 的知识侧优化：只取四件事

Status: implemented

## Problem

本项目与参考项目 `nashsu/llm_wiki` 同源：都出自 Karpathy 的 llm-wiki 方法论（三层 `raw → wiki → schema`，三个操作 ingest / query / lint）。但两边补的不是同一块——对方补**知识侧**（图谱与社区检测、多阶段检索、多模态、多格式解析），本项目补**安全侧**（草稿 → 差异 → 确认 → 回滚逐字节复原、审计线、三档门禁、五道自建门禁与负控制）。结果是本项目的工程纪律远超对方，知识侧却薄。四条现状是被量出来的：

1. **语义级在真机上从未执行过。** 真库 1,155 张整批一次提交实测 107.5 s，而部署的 `timeoutMs` 是 20000 —— 招牌指标（命中@1 = 13/20、命中@3 = 16/20）所依赖的两级，真机上不生效（详见[向量缓存那条](2026-10-02-vector-cache-outside-library.md)）。
2. **`wiki_links` 是死字段。** 导入脚本自述"565 条解析不出的目标留在 `wiki_links`，不参与门禁"，而插件代码从不读它。它是一份现成的"被提到、却没有卡"的清单。
3. **关系只有一跳、且不可遍历。** 图谱模型的四个信号（`related_concepts` / `source.path` / `type` / `domain_l2`）已经躺在每张卡里，只是没有任何地方把它们算成图。
4. **`[[双链]]` 的两种 Obsidian 写法读不出来。** 真库 5,513 条正文双链里 550 条是 `[[页名|别名]]`，旧实现把整串当名字解析，读者看到生标记。

## Decision

取了四件事，各有一条实现记录；另有一件被实测否决。

| 取 | 内容 | 记录 |
|---|---|---|
| ✅ | 分批嵌入 + 向量缓存落库外 + 启动预热 + 进度上报（改架构约束第 4 条） | [向量缓存落库外与启动预热](2026-10-02-vector-cache-outside-library.md) |
| ✅ | 门禁加 `wanted-card`（该建哪张卡）与 `island-domain`（哪个域进不去） | [门禁加两条规则](2026-10-02-two-lint-rules.md) |
| ✅ | 正文双链认下 `#锚点` 与 `\|别名` | [Obsidian 双链的两种写法](2026-10-02-obsidian-wikilink-forms.md) |
| ❌ | 图扩展当第四级召回 —— 20/20 题的金标本就在 40 席池内，瓶颈在精排排低了，不在召回 | [实测否决](../rejected/2026-10-02-graph-expansion-retrieval.md) |

否定那一条推翻了原计划里"第 5 条是唯二没试过的方向"的假设，也顺带把"三件套"收成了两条规则——另两条图度量（桥接卡、单向域对）的实测数字与被否的理由记在[门禁那条记录](2026-10-02-two-lint-rules.md)里。

## Alternatives considered

- **照搬 llm_wiki 的形态层**（Tauri 桌面壳、三栏布局、shadcn/ui、Zustand、Milkdown 编辑器）—— 落选：本项目是 Harness 插件，活在宿主的侧边栏入口与主面板席位里（[architecture.md](../../architecture.md)）。形态层既不可移植，也没有收益。
- **照搬 MCP Server + 本地 HTTP API 整套对外协议**（`127.0.0.1:19828` + Token 鉴权 + 随包 MCP）—— 落选：Harness 路由加七个智能体工具已经达成同一目的（外部工具与模型都能检索、读卡、跑门禁、看库状态），再加一层对外协议只增加攻击面与要维护的契约。
- **照搬 Louvain 社区检测与 sigma.js 图谱可视化 UI** —— 落选：源 vault 已经跑过 graphify（697 节点 / 1,429 边 / 61 个社区），而 `domain_l2` 本身就是人造社区；实测量出来的便宜度量里也只有孤岛域一条够格进门禁，重造社区检测和一块画布更不划算。
- **照搬多格式解析（PDF / DOCX / EPUB / MinerU）与多模态图片抽取** —— 落选：本项目刻意划了"插件不抓网页、不做 OCR、不做摘要"的边界，抽取归库外工具与模型。
- **照搬 `index.md` 作为 LLM 的导航入口** —— 落选：那是为"没有检索设施、靠先读目录文件再钻取"的场景设计的；本项目已有 BM25 + 向量 + 精排三级，`index/card-index.json` 又已经是机器索引且只作交叉核对。再加一份要人肉同步的内容目录，恰好违反"真源是磁盘上的卡片"这条约束。
- **加一个意图层（`purpose.md` 的对应物）** —— 落选：它要往库里加一个"约定文件"，与"真源是卡片"有张力；而"关键问题"其实已经以验收 20 题的形式存在（`tests/p1-cases.ts`），提升它是一笔独立的、收益不明显的账。
- **整体重构成 llm_wiki 那样的目录分层**（`entities/ concepts/ sources/ queries/ synthesis/ comparisons/`）—— 落选：本项目 `raw/` 只读不写、`cards/` 为真源、索引只作交叉核对，三层已经对齐；对方的目录按主题分，本项目按卡型（concept / rule / case / statute）加业务域分，是领域特化的正确取舍。

## Consequences

- 换来：招牌能力第一次在**部署配置下**成立（20 题全部走 `rerank`，修复前每题都是 `keyword`）；`wiki_links` 从死字段变成 34 条建卡清单；`商标` 这个 24 张卡的孤岛第一次被门禁看见；550 条别名式双链不再显示生标记。
- 换来：一条带数字的否决，把未来的检索投入指向精排侧而不是召回侧。
- 付出：改了架构约束第 4 条（向量缓存不再是"只在进程内存里"）与三条既有文档陈述（README 的门禁规则表、边界第 3 条、[TECH_DEBT](../../TECH_DEBT.md) 的两条缺口）。
- 仍未做：意图层、草稿携带归纳依据、多模态附图（都还在 Alternatives 或台账里）；精排侧怎么改没有定论；面板不轮询预热进度。
